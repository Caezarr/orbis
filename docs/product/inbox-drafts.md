# Inbox reply drafts (V1 Phase 1 backend + Phase 2 scheduler)

Status: backend built behind `ORBIS_INBOX_DRAFTS_ENABLED=false`. Not activated. Phase 2 (multi-tenant scheduler, continuous drafting, per-workspace caps, Today decisions) added on branch `feat/inbox-scheduler`. No live Composio, Gmail, Outlook or model call has been made. Updated 2026-10-02. Context: [17-v1-self-serve.md](../strategy/17-v1-self-serve.md) (branch `docs/v1-self-serve-plan`). Company sheet, ask-once questions and learning from edits (levels 3–5) build on this: see [company-brain.md](company-brain.md).

## What it does

For one connected Gmail or Outlook mailbox of a workspace:

1. Lists recent **inbound** mail (default 14 days, at most 50 messages).
2. Drops noise with deterministic rules, before any model call: no sender, own/sent messages, drafts, `no-reply`/`mailer-daemon`/`newsletter` senders, `List-Unsubscribe`/`List-Id`/`Precedence: bulk`, `Auto-Submitted`/`X-Autoreply`, "Automatic reply / Réponse automatique / Out of office" subjects, Gmail promotions/social/updates/forums categories.
3. Classifies the rest with a cheap model call: `customer_request`, `quote_request`, `supplier`, `admin`, `noise`.
4. For `customer_request` and `quote_request` only (max 5 per first run): skips threads the owner already answered, then generates a reply grounded in the confirmed website profile, owner-approved company sheet facts ([company-brain.md](company-brain.md)), approved workspace rules/memory, imported knowledge (BM25 over ready sources) and up to 3 of the owner's recent sent mails (tone only, never facts).
5. Creates the reply as a **draft** in the same thread, addressed to the original sender. **Never sends.**

Results (classification, draft preview, open questions, citations, draft id, link to the mailbox's drafts folder) are returned by `GET /api/v1/inbox`.

Honest limits of these controls: Gmail `gmail.compose` and Graph `Mail.ReadWrite` would technically allow sending or modifying mail if someone called those endpoints; the no-send guarantee is that this code path cannot call them. ## Data stored (migration 007)

`inbox_batches`: one row per worker job (provider, connected account id, mode, window, caps, status, aggregate stats, lease).
`inbox_messages`: per processed message — provider message/thread ids, SHA-256 content hash, classification, skip reason, flags, Orbis-generated draft preview (≤1,200 chars), open questions, citations (excerpts of the company's own sources), truncated subject (≤120 chars), draft receipt (draft id, payload/policy hash, state, attempts), token counts and estimated cost.

**No inbound email body is stored.** Bodies are held in memory during processing and sent to the model provider only. Justification: idempotency needs only ids + hash; the results screen needs our draft, not the customer's text (the user opens the thread in Gmail/Outlook). The subject preview and draft preview are nulled after `purge_after` (30 days) by the worker; rows keep only ids, hashes and receipts. The runtime role has no DELETE grant; tenant deletion cascades from `workspaces`.

## Worker

`scripts/operations-worker.ts` runs one task job and one inbox batch per invocation for a single configured workspace (`ORBIS_WORKER_JOB=all|tasks|inbox`, `ORBIS_WORKER_*_ID`), or one multi-tenant inbox pass (`ORBIS_WORKER_JOB=dispatch`, no identity env). Inbox batch: lease 5 min renewed per message, max 3 attempts, transient failure → re-queued with exponential backoff (1 min, then 4 min), connection/policy failure → `failed` with a generic message (and continuous drafting paused for that mailbox), lease lost → stops without finalizing, time budget reached → re-queued immediately **without consuming an attempt**. At most one running batch per workspace. Model calls happen outside DB transactions. Events: `inbox_batch_queued`, `inbox_batch_completed`, `first_draft_ready` (ids only).

## Multi-tenant scheduler (Phase 2)

Self-serve workspaces are processed without per-workspace configuration.

**Trigger.** `GET` or `POST /api/cron/inbox` with `Authorization: Bearer $CRON_SECRET` (constant-time comparison of SHA-256 digests; secret unset or shorter than 32 characters → 503; wrong → 401; no session, no tenant input; response = counts only). One bounded pass per call: `maxDuration = 60`, pass budget `ORBIS_SCHEDULER_BUDGET_MS` (50 s), no new batch or message starts with less than `ORBIS_SCHEDULER_RESERVE_MS` (15 s) left. A message already in flight may still take up to the model timeout; if the function is killed, the lease expires and the batch is retried (idempotent). The CLI `ORBIS_WORKER_JOB=dispatch` runs the same pass.

**Schedule.** The repo has no `vercel.json`; nothing is added so deploys are unchanged. To schedule on Vercel, add:

```json
{ "crons": [{ "path": "/api/cron/inbox", "schedule": "*/5 * * * *" }] }
```

and set `CRON_SECRET` in the project env (Vercel sends it as the bearer token). Every 5 minutes keeps a 15-minute poll interval accurate to ±5 min. Vercel Hobby only allows daily crons; on Hobby use an external scheduler calling the route with the bearer header, or the CLI from a supervisor.

The migration owner is granted the two NOLOGIN roles `WITH INHERIT FALSE, SET TRUE` (PostgreSQL 16+) only so it can assign function ownership; it does not inherit their policies. On PostgreSQL < 16 the grant is a plain membership. FORCE RLS stays on everywhere: even the table owner cannot write `inbox_settings` directly without a context.

**Processing.** For each discovered workspace the dispatcher calls the existing worker with that identity: `scoped()` sets `app.user_id/tenant_id/workspace_id` transaction-locally and re-verifies the membership before any query. A stale or forged id processes nothing. Every content query keeps explicit `workspace_id/tenant_id` filters on top of RLS.

**Fairness and exclusivity.** Workspaces are served oldest-due first, round-robin (one batch per workspace per round), at most `ORBIS_SCHEDULER_MAX_PER_WORKSPACE` (2) per workspace and `ORBIS_SCHEDULER_MAX_BATCHES` (10) per pass, `ORBIS_SCHEDULER_MAX_WORKSPACES` (50) discovered per pass. A claim takes a per-workspace advisory transaction lock, refuses while another batch of that workspace holds a live lease, then `FOR UPDATE SKIP LOCKED` + lease token: concurrent passes never process the same batch (verified with three concurrent passes on PostgreSQL 16). One failing workspace is counted and skipped; it never blocks the others.

**Continuous drafting.** Explicit per-workspace opt-in (`inbox_settings.continuous_enabled`, default off), enabled by an owner/admin from the end of the `/start` results or the Today page, and only after a completed first run (the mailbox of that first run is used). Copy shown: « Orbi vérifie votre boîte toutes les 15 minutes et prépare des brouillons. Rien n’est envoyé. » When due (`next_run_at`), the dispatcher enqueues one `incremental` batch (request key per account and 15-min slot; not stacked while one is pending) with `since_at = cursor − 5 min`; Gmail lists with `after:<epoch>`, Outlook with `received_date_time_ge`, and older messages are dropped in code as well. Dedup is the existing `(workspace, account, message, mission version)` row + draft idempotency key. On completion the cursor moves to the newest message handled, or just before the oldest message still waiting (draft quota reached, uncertain draft). Budget exhaustion or a yield leaves the cursor unchanged. A mailbox policy failure pauses continuous drafting. Up to `ORBIS_INBOX_CONTINUOUS_MAX_DRAFTS` (10) drafts per incremental batch.

**Per-workspace caps.** Effective cap = stored `monthly_cap_cents` (operator: `SELECT orbis_set_workspace_inbox_cap('<workspace>', <cents|NULL>)` as the migration owner; later tied to plans) → else `ORBIS_WORKSPACE_MONTHLY_CAP_CENTS` → else `ORBIS_OPERATIONS_MONTHLY_CAP_CENTS`; always `min(…, ORBIS_OPERATIONS_MONTHLY_CAP_CENTS)`. Enforced in `reserveInboxBudget` before every model call (reserved/settled accounting unchanged). A stored `0` blocks inbox model spend for that workspace. Note: the global value is a per-workspace ceiling, not a platform-wide sum.

**Today decisions.** `GET /api/v1/inbox/today` (session) returns, since the user's last « Marquer comme vu » (`POST`, table `inbox_visits`, default: last 7 days): drafts ready to review (10 latest, same card as `/start`), drafts with open questions, messages to check, messages left aside, plus the continuous-drafting settings. `GET/PUT /api/v1/inbox/settings` (`{continuousEnabled}` strict; PUT owner/admin). Shown at the top of `/today` only when inbox drafts are enabled. No email digest yet.

## Activation steps

1. Review and merge; back up the database; run `scripts/migrate.ts` with `DATABASE_APP_ROLE` (grants `inbox_batches`, `inbox_messages`, column-scoped `inbox_settings`, `inbox_visits`, EXECUTE on the discovery function). The migration owner needs CREATEROLE (008 creates two NOLOGIN roles) and must own or have grant rights on schema `public`. Run `scripts/check-platform.ts --database` (checks inbox + scheduler RLS and the dispatcher privilege model).
2. **Gmail auth config** in Composio with exactly `https://www.googleapis.com/auth/gmail.readonly` and `https://www.googleapis.com/auth/gmail.compose` (Composio: pass scopes in the auth config `credentials.scopes`). Do not add `gmail.send`, `gmail.modify` or `https://mail.google.com/`. Set `COMPOSIO_AUTH_CONFIG_GMAIL`, `COMPOSIO_TOOLKIT_GMAIL=gmail`, `COMPOSIO_TOOL_VERSION_GMAIL=20260915_00` (or the version you validate).
3. **Outlook auth config** with delegated `Mail.ReadWrite`, `User.Read`, `offline_access` — **not** `Mail.Send`. Microsoft has no compose-only scope; creating a draft reply needs `Mail.ReadWrite`. Expect tenant admin consent for some business tenants (Composio Outlook FAQ). Set `COMPOSIO_AUTH_CONFIG_OUTLOOK`, `COMPOSIO_TOOLKIT_OUTLOOK=outlook`, `COMPOSIO_TOOL_VERSION_OUTLOOK=20260929_00`.
4. Set `ORBIS_OPERATIONS_MONTHLY_CAP_CENTS` (hard ceiling per workspace), optionally `ORBIS_WORKSPACE_MONTHLY_CAP_CENTS` (default per workspace) and per-workspace caps via `orbis_set_workspace_inbox_cap`, model provider env, optionally `ORBIS_AI_CLASSIFIER_MODEL` (same provider) and the cost estimates once real per-call cost is measured.
5. Set `CRON_SECRET` (≥32 chars) and schedule `/api/cron/inbox` (see Multi-tenant scheduler). Enable `ORBIS_INBOX_DRAFTS_ENABLED=true` with `ORBIS_INBOX_MODE=test` on staging; connect a test mailbox; `POST /api/v1/inbox`; let the cron (or `ORBIS_WORKER_JOB=dispatch`) run; check classifications and simulated drafts, and validate the response shapes listed above.
6. Switch staging to `ORBIS_INBOX_MODE=scoped_autonomy`; verify drafts appear in the right thread, addressed to the sender, nothing in Sent; kill the worker mid-draft and re-run to observe reconciliation; revoke the connection mid-batch.
7. Only then production.

## Google verification / CASA — what Composio documents

- Gmail toolkit page: "Composio-managed OAuth available? Yes". Adding scopes beyond the defaults can trigger Google's "App is blocked" screen; the documented fix is to remove the extra scopes or "create your own OAuth app and submit the scopes for verification".
- Gmail KB guide: `gmail.send` "is a granular sensitive scope and requires Google verification" (we do not request it).
- [Managed vs custom auth](https://docs.composio.dev/docs/custom-app-vs-managed-app): managed apps suit development; for production, switch to your own credentials (consent screen shows "Composio" otherwise; managed apps share rate-limit quota).
- Composio's docs that were reviewed **do not state** which default scopes the managed Gmail app requests, whether that app is verified for `gmail.readonly`/`gmail.compose`, or whether using it removes the need for a CASA assessment on our side. This is an open question for Composio support; do not assume coverage. Google's own policy on restricted Gmail scopes should be checked directly before launch.

## Known limits / follow-ups

- Calendar-aware drafts (slots from free/busy) and visible triage (Orbis labels/categories): see [inbox-calendar-labels.md](inbox-calendar-labels.md).
- Company brain (migration 009): open `[[À CONFIRMER]]` placeholders become deduplicated questions, a sent-mail extraction is queued once after the first completed run, and incremental batches check draft outcomes. See [company-brain.md](company-brain.md).

- Response shapes are untested against real accounts (see above). Gmail reconciliation scans one page of 100 drafts.
- A message whose draft is `uncertain` is regenerated on the next run before reconciliation (one extra model call) because the full draft text is not stored.
- Rows already terminal are not re-attached to a later batch, so `GET` for a new batch shows only messages processed in that batch.
- Contact-form notifications (sender `no-reply@…` with customer in `Reply-To`) are skipped by design; supporting them needs a verified form-sender allowlist.
- No HTML drafts (Outlook `comment` is plain text); placeholders are `[[…]]` text markers rather than color highlighting.
- Classification and draft quality are unmeasured; no live model run has been done.
- Scheduler: only inbox batches are multi-tenant; durable tasks (`runOneTask`) still use the single configured workspace. No email digest (in-app Today only). Polling cost: each incremental batch re-lists the mailbox even when the workspace is over budget (no model call is made). The global cap is per workspace, not a platform-wide total.

## Plans and quotas (V1 Phase 3)

Every batch is gated by the workspace entitlement ([billing-v1.md](billing-v1.md)). Without an active trial/plan or without drafts left: `POST /api/v1/inbox` returns 402 with a French reason; the dispatcher queues no continuous batch (drafting shows as paused, resumes automatically); the worker ends an already-queued batch as `plan_inactive` or `quota_reached` before any mailbox/model call. Mid-batch, the pipeline stops before the next message when the plan's drafts are used (`quota_reached`, partial results kept, cursor not advanced). Past drafts stay readable in every state.

## Prompt-injection red team (Phase 4)

Suites: `src/lib/security/redteam/*.test.ts`, corpus in `src/lib/security/redteam/fixtures.ts`, shared detection helpers in `src/lib/security/untrusted-text.ts`. All models are mocks that **obey** the injection (they return the attacker's link/address/phone/price, extra fields such as `recipient`, `cc`, `bcc`, `send: true`, oversized or wrongly typed fields). No network, no provider, no Composio.

**Corpus.** 20 hostile inbound emails (EN/FR instruction overrides, Reply-To divergence, cc/bcc demands, markdown links and image beacons, bare domains `evil.test/collect?d=…` and `evil-site.com`, lookalike sub-domains with secrets in the query, fake `SYSTEM:` lines, fake tool-call JSON, fake `</ORBIS_DATA_…>` closing tags, Cyrillic homoglyph domains/emails, fullwidth `＠`, zero-width characters inside URLs/emails/phones, U+202E bidi override, defanged `evil[.]test` / `boss(at)evil.test` / `hxxps://`, a 100k-char email with the payload at the end, `<a href>`, `<img src>`, `<script>`, instruction HTML comments, fake `[[À CONFIRMER : http://…]]` placeholders, attacker data in model *questions*, invented prices and discounts, three invalid output shapes); one hostile public page for `/start`; three hostile owner sent mails (instruction pasted in the owner's own text, a `---------- Forwarded message ---------` block, third-party PII).

**What is asserted (real code paths).**
- `processMailboxBatch` with a fake mailbox (a proxy that refuses any method other than `listInbound`, `listSent`, `readThread`, `createReplyDraft`) and an in-memory store: every `createReplyDraft` recipient is the original From address; Reply-To divergence → `needs_review`, no draft, no draft-model call; invalid or oversized model output (and an off-schema classification) → `failed`, no draft; extra output fields have no effect; no attacker URL/domain/email/phone/unsupported amount survives in the draft body, the stored preview, stored questions or brain questions; invisible/bidi characters never reach the draft; non-verbatim citations are dropped; no inbound text is stored (canary), preview ≤ 1 200 chars, flags are signal ids only. `assertMailboxPolicy` refuses SEND/FORWARD/REPLY_ALL/DELETE/MODIFY slugs for every operation.
- `buildStartPreview` on the hostile page: instruction sentences never reach the model prompt, answers are verbatim instruction-free page quotes, example emails and drafts carry no attacker contact or invented figure; off-schema output → quote-only view.
- Brain: `buildCandidate` / `processExtraction` drop non-verbatim and instruction quotes, never let a statement add a link/domain/email/phone/figure absent from its verified quotes, redact third-party PII, never set a status (nothing auto-approved).
- Follow-ups: `runFollowups` drafts only to the pipeline contact with the guard applied to body and questions; invalid output → failed, no draft. `verifyRequest` / `trackRequest`: the `need` summary (and budget/deadline quotes) cannot carry contact data, instructions or figures absent from the quote.
- Pathological inputs (6 000-char dotted/digit/`@`/`[[`/`<a` bodies, 100k-char email) stay under 1 s.

**Gaps found and fixed.**
1. `guardDraft` did not guard `questions`, and prepended them unguarded into the body when it had no placeholder → questions now go through the same scrub (neutral inline markers), questions that are instructions are dropped, placeholders whose content is an instruction are neutralised.
2. Bare domains (`evil.test/collect?d=x`, `evil-site.com`) passed → detected (known-TLD list, punycode, or any TLD followed by a path; title-case "fait.Il" is not a domain) unless present in trusted text.
3. ASCII-only patterns: homoglyph, fullwidth-`@`, zero-width and bidi tricks passed → model text is compatibility-folded (fullwidth/small-form/math/enclosed only, so `m²` and `…` stay), invisible/bidi characters (U+200B–U+200F, U+202A–U+202E, U+2060–U+206F, U+FEFF, …) are stripped, defanged forms are undone, patterns are unicode-aware, dotted tokens with Cyrillic/Greek letters are treated as links.
4. **Residual limits (honest).**
- Owner-written text is trusted: a URL/amount the owner pasted into their own reply without quote headers can become a brain *candidate* (still needs a human click) and, for follow-ups, the owner's last message is a trusted source for the draft guard.
- The `/start` page is the visitor's "company" source: a contact on that page that is not inside an instruction-like sentence is trusted (shown only to that visitor).
- Spelled-out obfuscation ("boss at evil dot com", "zéro six…"), non-Latin digits (Arabic-Indic), and homoglyphs from scripts other than Cyrillic/Greek are not detected. Amounts written in words ("mille euros") are not guarded.
- Signals are heuristics; the protection is structural (no tools, recipient by code, schema validation, deterministic guard, human review of every draft), not the classifier.
- Model *prose* that follows an instruction without contact data or figures (e.g. a rude or off-topic sentence) is not detected; the owner reviews every draft.
- Bare-domain detection can mark a legitimate unknown domain as `[[À CONFIRMER : lien]]` (false positive by design).
